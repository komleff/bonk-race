## 10. Архитектура

### 10.1 Принцип: клиент считает, сервер валидирует

Для одиночного заезда на время серверная симуляция в реальном времени избыточна. Клиент рассчитывает физику локально. У игрока нет задержек, интерполяции и связанных с сетью проблем.

### 10.2 Поток данных

```
┌──────────────────────────────────────────────────────────┐
│                       КЛИЕНТ                              │
│  1. Загрузка: GET /api/v1/tracks/today → конфигурация     │
│  2. Загрузка: GET /api/v1/ghosts?trackId=X → призраки     │
│  3. Локальная симуляция: физический движок (`fixedDeltaTime`) │
│  4. Запись входных данных заезда                           │
│  5. Финиш: POST /api/v1/runs/submit → результат, запись   │
│     заезда, хэш                                           │
└───────────────────────────┬──────────────────────────────┘
                            │ HTTPS
                            ▼
┌──────────────────────────────────────────────────────────┐
│                       СЕРВЕР                              │
│  1. Приём результата + записи заезда                      │
│  2. Базовая валидация: время больше теоретического         │
│     минимума, чекпоинты в правильном порядке              │
│  3. Запись в таблицу лидеров (если новый рекорд)          │
│  4. Хранение записи заезда для призрака                   │
│  5. Асинхронная пересимуляция (для верхних строк          │
│     таблицы лидеров)                                      │
└──────────────────────────────────────────────────────────┘
```

Фактический формат данных определён в `shared/src/types.ts` (`RunResult`, `GhostFrame`).

Авторитативные данные — входные команды игрока. Кадры призрака — производный артефакт после валидации.

### 10.3 Уровни валидации

| Уровень | Что проверяется | Когда |
| --------- | --------------- | ------- |
| 1 — Базовый | Время больше теоретического минимума, чекпоинты, формат данных | Каждый заезд |
| 2 — Пересимуляция | Сервер проигрывает запись заезда на копии движка, сравнивает время | Верхние строки таблицы лидеров |
| 3 — Выборочный | Случайная выборка + подозрительные результаты | Фоновый процесс |

### 10.4 Технический стек

Клиент-серверная архитектура с разделяемым модулем физики. Детали технологического стека описаны в архитектурной документации (`docs/soft-launch/SlimeArena-Architecture-v4.2.5-Part1.md`).

### 10.5 Фиксированный шаг симуляции на клиенте

Физика обновляется с `fixedDeltaTime` (1/30 или 1/60 сек) в цикле с накоплением. Рендер интерполирует между кадрами. Результаты идентичны на мониторах с любой частотой обновления (60/120/144/165 Гц).

## 11. Требования к UI

### 11.1 Визуальная читаемость

- Безопасные стены: синие/зелёные, мягкие формы.
- Опасные стены: красные, с шипами/свечением.
- Бустеры: жёлтые, с анимацией пульсации.
- Монеты: золотые звёздочки, с искрящимся эффектом.
- Призрак: полупрозрачный (40%), с именем над ним.
- Призрак личного рекорда: полупрозрачный (30%), без имени.

### 11.2 Интерфейс во время заезда (минимальный)

- Таймер (крупный, сверху по центру).
- Текущая / лучшая разница времени с призраком (± сек, зелёный/красный).
- Счётчик монет (мелкий, угол).

### 11.3 Адаптация под Yandex Games

- Крупные кнопки (минимум 48×48 dp).
- Увеличенный шрифт в меню.
- Полная русская локализация.
- Нет мелкого текста в интерфейсе заезда.

**Платформенные ограничения CrazyGames:** кнопка рекламы с вознаграждением не появляется на экране гонки.
