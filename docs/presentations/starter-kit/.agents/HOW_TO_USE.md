# Как пользоваться рабочим местом ИИ-агентного инженера

Инструкция для человека-оператора. Стартер-кит настроен — что дальше?

---

## Ежедневный рабочий процесс

### 1. Начало сессии

```bash
claude                              # Запустить Claude Code
```

Claude Code автоматически прочитает `CLAUDE.md` и загрузит контекст. Если используете Beads:

```bash
bd ready                            # Посмотреть доступные задачи
bd show <id>                        # Детали задачи
bd update <id> --status=in_progress # Взять в работу
```

### 2. Активация роли

Скажите агенту, кем он работает:

```
Ты PM. Прочитай .agents/AGENT_ROLES.md секция "0. Project Manager".
Задача: [описание]
```

| Роль | Когда использовать |
|------|-------------------|
| **PM** | Планирование спринта, координация, запуск ревью |
| **Architect** | Декомпозиция задач, архитектурные решения |
| **Developer** | Написание кода, исправление багов |
| **Reviewer** | Проверка PR |

### 3. Типичные сценарии

**Сценарий A: Одиночная задача**
```
Ты Developer. Прочитай .agents/AGENT_ROLES.md секция "2. Developer".
План утверждён. Задача: [описание].
```
→ Агент пишет код → коммит → PR → вы проверяете и мержите.

**Сценарий B: Спринт с PM**
```
Ты PM. Прочитай .agents/AGENT_ROLES.md секция "0. Project Manager".
Задача: спланировать спринт по задачам из бэклога.
```
→ PM создаёт план → вы утверждаете → PM запускает Developer-субагентов → ревью → merge.

**Сценарий C: Кросс-ревью (внешняя модель)**

Скопируйте diff PR и вставьте в GPT/Gemini вместе с промптом ревью (см. ниже).

### 4. Завершение сессии

Напомните агенту:
```
Обнови .memory_bank/activeContext.md — что сделано, что в работе, какие проблемы.
```

Если используете Beads:
```bash
bd close <id> --reason="PR #N"      # Закрыть задачу
bd sync                              # Синхронизировать с git
```

## Промпты активации ролей

### Формат

```
Ты [Роль]. Прочитай .agents/AGENT_ROLES.md секция "[номер и название]".
Задача: [описание]
```

### Примеры

**PM — планирование:**
```
Ты PM. Прочитай .agents/AGENT_ROLES.md секция "0. Project Manager".
Задача: спланировать спринт по задачам из бэклога. Создать план и согласовать со мной.
```

**PM — запуск ревью:**
```
Ты PM. Прочитай .agents/AGENT_ROLES.md секция "0. Project Manager".
Задача: запустить ревью PR #42, собрать вердикты от субагентов.
```

**Developer:**
```
Ты Developer. Прочитай .agents/AGENT_ROLES.md секция "2. Developer".
План утверждён. Задача: реализуй [описание задачи].
```

**Reviewer:**
```
Ты Reviewer. Прочитай .agents/AGENT_ROLES.md секция "3. Reviewer".
Задача: проверь PR #42 по трём аспектам (архитектура, безопасность, качество).
Результат: выполни `gh pr comment 42 --body "..."` — НЕ выводи отчёт в чат.
```

## Внешние ревьюверы (GPT, Gemini)

Для ревью в другой модели: скопируйте diff (`gh pr diff <N>`) и вставьте в чат вместе с промптом:

```
Ты Code Reviewer. Твоя роль — ТОЛЬКО ревью. Ты НЕ правишь код.

Проверь следующий diff по трём аспектам:
1. Архитектура — соответствие принципам проекта
2. Безопасность — инъекции, валидация входных данных
3. Качество — читаемость, тесты, edge-cases

Формат ответа:
## Вердикт: APPROVED / CHANGES_REQUESTED
### Архитектура: OK / ISSUE
### Безопасность: OK / ISSUE
### Качество: OK / ISSUE
### Комментарии: [список замечаний]

ВАЖНО: Ты НЕ пишешь и НЕ правишь код. Только анализ и вердикт.

Diff для ревью:
[вставить diff]
```

> **Совет:** для Gemini обязательно добавляйте «НЕ правишь код» — он склонен игнорировать это ограничение.

---

## Вердикты ревью

| Вердикт | Что делать |
|---------|-----------|
| `APPROVED` | Можно мержить (рекомендуется 2+ от разных моделей) |
| `CHANGES_REQUESTED` | Вернуть Developer на исправление |
| `ESCALATION` | Сменить модель или решить вручную |

## На что обратить внимание

1. **Напоминайте про Memory Bank.** После compaction агент может забыть обновить `activeContext.md`. Напоминайте явно.
2. **Напоминайте про язык.** Если правило о языке комментариев важно — повторяйте его в промпте. После compaction оно выпадает первым.
3. **Merge — только вы.** Агенты физически не могут пушить в main (deny-list в settings.json). Это ваша ответственность.
4. **Проверяйте публикацию отчётов.** Ревьюверы и PM могут забыть опубликовать отчёт в PR через `gh pr comment`. Следите.
5. **Рефакторинг раз в 2 недели.** Агенты склонны к God Objects. Планируйте ревизию кода регулярно.
