## Часть 3. Процесс: от идеи до деплоя (8 мин)

1. **Plaud** — запись обсуждения идеи → автоматическая расшифровка и summary
2. **GPT Pro (Thinking)** — deep research: рынок, конкуренты, аудитория
3. **Opus** — составление GDD (модульная структура: Core, Arena, Combat, Economy, UI...)
4. **Кросс-ревью GDD** — GPT, Gemini, DeepSeek (2–4 итерации)
5. **Opus** — архитектурный документ на базе GDD
6. **Кросс-ревью архитектуры** — те же модели, до консенсуса

### Фаза B: Настройка рабочего места (шаги 8–9)

7. **GitHub** — fork/создание репо, branch protection, CODEOWNERS, CI/CD
8. **Настройка окружения ИИ-агентов** — подробно в Части 4

### Фаза C: Разработка (шаги 10–19)

9. **PM-Opus** планирует спринт → согласование с оператором
10. **Developer-субагенты** реализуют задачи
11. **Reviewer-субагенты** — ревью по 3 аспектам (архитектура, безопасность, качество)
12. **Внешние ревьюверы** — GPT-5.4, Codex, Copilot (ручной запуск)
13. **Автотесты** → **Ручное тестирование** → **Merge** (только оператор)
14. **Release** → **Deploy** (GitHub Actions + Docker)

### PR как средство коммуникации между агентами

> **Ключевой инсайт:** Pull Request — это не просто мерж-реквест, а **шина обмена информацией** между разными ИИ-агентами.

```
Developer (Opus) ──push──► PR #42
                              │
PM (Opus) ──────── gh pr comment ──► "Developer Report: ..."
                              │
Reviewer 1 (Opus) ─ gh pr comment ──► "Review: APPROVED"
Reviewer 2 (GPT)  ─ gh pr comment ──► "Review: CHANGES_REQUESTED"
Reviewer 3 (Gemini)─ gh pr comment ──► "Review: APPROVED"
                              │
PM (Opus) ──────── парсит комменты ──► консенсус 2/3 → делегирует фикс
                              │
Developer (Opus) ──push──► фикс
                              │
Reviewers ──────── ре-ревью ──► консенсус 3/3 ✅
                              │
Оператор (человек) ──────── merge
```

**Почему PR, а не чат:**
- Аудиторский след (кто, когда, какой вердикт)
- Разные модели (GPT, Gemini, Opus) пишут в одно место
- PM парсит JSON-метаданные из комментариев для автоматизации
- Оператор видит всю историю решений в одном месте

## Часть 4. Файлы настроек — подробный разбор (8 мин)

### 4.1 Какая модель читает какие файлы

```
┌─────────────────────────────────────────────────────────────────┐
│                     Файлы проекта                               │
├─────────────────────┬───────────┬──────────┬──────────┬────────┤
│ Файл                │ Claude    │ Copilot  │ Cursor   │ GPT/   │
│                     │ Code      │          │          │ Gemini │
├─────────────────────┼───────────┼──────────┼──────────┼────────┤
│ CLAUDE.md           │ ✅ авто   │ ❌       │ ⚙️ rule  │ ❌     │
│ CLAUDE-core.md      │ ✅ по ссыл│ ❌       │ ❌       │ ❌     │
│ CLAUDE-*.md         │ ✅ по ссыл│ ❌       │ ❌       │ ❌     │
│ .claude/settings    │ ✅ авто   │ ❌       │ ❌       │ ❌     │
│ copilot-instr.md    │ ❌        │ ✅ авто  │ ❌       │ ❌     │
│ .cursorignore       │ ❌        │ ❌       │ ✅ авто  │ ❌     │
│ .agents/*.md        │ ✅ по ссыл│ ✅ по ссыл│ ✅ по ссыл│ 📋 вруч│
│ .memory_bank/*.md   │ ✅ по ссыл│ ❌       │ ✅ индекс│ 📋 вруч│
│ config/balance.json │ ✅        │ ✅       │ ✅       │ 📋 вруч│
└─────────────────────┴───────────┴──────────┴──────────┴────────┘

✅ авто  = читает автоматически при запуске
✅ по ссыл = читает по ссылке из корневого файла
⚙️ rule  = нужно настроить как project rule
📋 вруч  = вставляется вручную в контекст промпта
```

**Как совмещать:** каждый инструмент читает свой "корневой" файл, но `.agents/AGENT_ROLES.md` — универсальный документ, на который ссылаются все. Это точка конвергенции.

### 4.2 `.claude/settings.json` — разбор настроек

```jsonc
{
  "permissions": {
    "allow": [
      "Bash(*)",        // Все bash-команды (защита через deny-list ниже)
      "Read", "Edit", "Write",  // Файловые операции
      "Glob", "Grep",   // Поиск файлов и текста
      "WebFetch", "WebSearch",  // Интернет (для research)
      "TodoWrite",       // Управление задачами в сессии
      "Task",            // Запуск субагентов
      "NotebookEdit"     // Jupyter-ноутбуки
    ],
    "deny": [
      // 🔒 Защита секретов
      "Read(.env*)",              // .env файлы с API-ключами
      "Read(**/credentials*)",    // Файлы с учётными данными
      "Read(**/secrets*)",        // Файлы с секретами

      // 🔒 Защита от удаления (Linux + Windows)
      "Bash(rm -rf:*)",           // Рекурсивное удаление
      "Bash(rm *)",               // Удаление файлов
      "Bash(del *)",              // Windows: удаление файлов
      "Bash(rmdir *)",            // Windows: удаление директорий

      // 🔒 Защита git (КРИТИЧНО)
      "Bash(git push --force *)", // Force push
      "Bash(git push -f *)",      // То же, короткая форма
      "Bash(git push origin main)", // Push в main

      // 🔒 Защита GitHub (только человек мержит)
      "Bash(gh pr merge *)",      // Автоматический merge PR
      "Bash(gh repo delete *)",   // Удаление репозитория
      "Bash(gh api -X DELETE *)"  // DELETE-запросы к GitHub API
    ],
    "defaultMode": "acceptEdits"  // Авто-принятие правок файлов
  },
  "language": "russian",               // Русский язык ответов
  "alwaysThinkingEnabled": true        // Extended thinking (глубокий анализ)
}
```

**Зачем deny-list:**
- Агент физически не сможет выполнить `git push origin main` — даже если в промпте ошибка
- Это **второй уровень защиты** после правил в `AGENT_ROLES.md`
- Правила можно обойти (агент "забудет"), а deny-list — нельзя

### 4.3 `.github/copilot-instructions.md` — зачем отдельный файл

Copilot **не читает** `CLAUDE.md`. У него свой файл: `.github/copilot-instructions.md`.

Содержит **подмножество** правил из CLAUDE.md, адаптированное под Copilot:
- Русский язык комментариев
- Структура проекта (монорепо, Colyseus, Canvas 2D)
- Ключевые паттерны (детерминизм, 30 ticks/sec, Rng)
- Правило: баланс только в `balance.json`
- Ссылка на `.agents/AGENT_ROLES.md`

### 4.4 `.cursorignore` — что и зачем исключаем

Cursor индексирует всё содержимое проекта. Без `.cursorignore`:
- Индексирует `node_modules/` (тысячи файлов)
- Тратит контекстное окно на `dist/`, логи, бэкапы БД

Исключаем: `node_modules/`, `dist/`, `logs/`, `*.db`, `.env`
Оставляем: `docs/`, `.agents/`, `.memory_bank/`, все `.md` файлы

### 4.5 Memory Bank — внешняя память между сессиями

| Файл | Обновляется | Кем |
|------|-------------|-----|
| `projectbrief.md` | Редко | Оператор |
| `productContext.md` | Редко | Оператор |
| `techContext.md` | При смене стека | Developer |
| `systemPatterns.md` | При архитектурных решениях | Architect |
| **`activeContext.md`** | **Каждую сессию** | **PM / Developer** |
| **`progress.md`** | **Каждый спринт** | **PM** |

**Без Memory Bank:** агент каждую сессию начинает с нуля, переоткрывает те же решения, не знает контекста.
**С Memory Bank:** агент читает `activeContext.md` и сразу понимает, что было сделано, что в работе, какие проблемы.

### 4.6 Beads — задачи как код

```yaml
# .beads/config.yaml
sync-branch: "beads-sync"    # Ветка для синхронизации задач
```

Beads хранит задачи в `.beads/issues.jsonl` (JSONL) + SQLite. Агенты работают с задачами через CLI:
```bash
bd ready                          # Доступные задачи
bd update <id> --status=in_progress  # Взять в работу
bd close <id> --reason="PR #42"     # Закрыть с причиной
```

**Альтернативы:** GitHub Issues, Linear, Jira — но Beads оптимален для CLI-first агентов.

## Часть 5. Что не удалось победить — честный разбор (5 мин)

### 5.1 Итерационный цикл ревью обрывается

**Проблема:** PM запускает цикл код → ревью → фикс, но после первого исправления цикл останавливается. Реально нужно 3–7 итераций.

**Пример из Bonk Race:** PR #5 прошёл 4 итерации ревью (GPT-5.3), и на итерации 3 те же P0/P1 баги всё ещё присутствовали — Developer не применял фиксы полностью.

**Текущее решение:** ручной запуск каждой итерации оператором.
**Идеальное решение:** `pm_orchestrator.py --cycle --max-iterations=5` (документирован в PM_ROLE.md, но на практике PM не всегда запускает полный цикл).

### 5.2 Английский язык в комментариях

**Проблема:** правило "комментарии только на русском" прописано в CLAUDE.md, AGENT_ROLES.md, copilot-instructions.md — но агенты регулярно его игнорируют. Исправление требует отдельного PR и много токенов.

**Доказательство:** PR #21 — "docs: enforce Russian code comments rule for all AI agents" — отдельный PR только на исправление языка комментариев.

**Почему так:** модели обучены на англоязычном коде, комментарии на русском — "неестественны" для модели. Правило работает ~70% случаев, остальное — ручная коррекция.

### 5.3 God Objects — ArenaRoom.ts (3700+ строк) и main.ts (4000+ строк)

**Проблема:** агенты создали монолитные файлы вместо декомпозиции на модули. Рефакторинг запланирован, но каждое изменение рискует сломать 16 систем с фиксированным порядком выполнения.

**Причина:** агенты следуют принципу "минимальное изменение" из CLAUDE-core.md и добавляют код в существующий файл, а не создают новый модуль.

### 5.4 Безопасность: агенты не ловят уязвимости

**Из реальных ревью Bonk Race:**
- **Coin farm** (P0) — клиент контролирует `coinsCollected` и `finishMs`, можно фармить валюту. Найдено GPT-5.3, не исправлено за 3 итерации.
- **Идемпотентность** (P1) — `operationId` отправляется клиентом, но сервер его не проверяет. Можно дублировать награды.
- **Guest auth** (P1) — гостевой токен проходит `requireAuth`, но профиль не создаётся → 500 error.

**Вывод:** один ревьювер недостаточно. Кросс-ревью разными моделями критично именно для безопасности.

### 5.5 Docker и инфраструктура — каскадные сбои

- **v0.3.1** — ошибка отсутствия файла конфигурации (withdrawn)
- **v0.3.2** — ESM/CommonJS mismatch (withdrawn)
- **v0.3.3** — 9 исправлений (D-01..D-09)
- **Slime Arena v0.8.5** — Redis MISCONF: `stop-writes-on-bgsave-error` заблокировал все записи → 22 часа даунтайма

**Вывод:** ИИ-агенты плохо справляются с инфраструктурой. DevOps-задачи требуют человеческого контроля.

### 5.6 Gemini как ревьювер — неуправляем

- Получает промпт "ты ТОЛЬКО ревьюишь, НЕ правь код"
- Начинает править код
- Выдаёт ложно-положительные ревью (APPROVED с пропущенными P0-багами)
- **Вывод:** Gemini можно использовать для cross-check, но его вердиктам нельзя доверять

### 5.7 Агенты не учатся на ошибках предыдущих итераций

PR #5: одни и те же баги (coin farm, guest auth) присутствовали в итерациях 1, 2, 3.
Developer-агент получал отчёт ревьювера, но либо не применял фиксы, либо применял частично.

**Причина:** каждый субагент запускается в чистом контексте и не видит историю предыдущих итераций целиком.

```bash

# 2. Переименовать шаблоны (.template → готовый файл)
find . -name "*.template" -exec sh -c \
  'mv "$1" "${1%.template}"' _ {} \;

# 3. Заменить плейсхолдеры [PROJECT_NAME], [BUILD_CMD], [TEST_CMD]

# 4. Заполнить Memory Bank (projectbrief.md, techContext.md)

# 5. Запустить Claude Code

```

1. **Минимальный** — `CLAUDE.md` + `settings.json` → один агент

3. **Полный** — + `.agents/` + `.memory_bank/` → мультиагентная разработка

## Визуальное оформление презентации

### Стиль
- Тёмная тема (dark mode)
- Минималистичные слайды с крупными заголовками
- Иллюстрации: схемы потоков (Mermaid → SVG), скриншоты IDE
- Персонаж-аватар докладчика — стилизованный образ (MidJourney / Figma)

### Персонаж
Нужно сгенерировать через MidJourney или Figma:
- Стилизованный аватар докладчика
- Появляется на вводном слайде и в ключевых моментах
- Стиль: профессиональный, но дружелюбный (cartoon/3D character)
- Можно использовать как "гида" по презентации

### Рекомендуемые иллюстрации по слайдам

| Слайд | Иллюстрация |
|-------|-------------|
| Титульный | Аватар + название доклада |
| Vibe vs Agentic | Две колонки с иконками |
| Стек моделей | Логотипы моделей + роли |
| Процесс | Горизонтальная timeline с иконками фаз |
| Какая модель какой файл | Таблица с цветовыми маркерами |
| PR как шина | Схема потока (Mermaid) |
| settings.json | Скриншот кода с подсветкой |
| Трудности | Красные/жёлтые warning-блоки |
| Стартер-кит | Скриншот дерева файлов |

### Инструменты для создания
- **Figma** — верстка слайдов (можно через MCP)
- **MidJourney** — аватар персонажа
- **Mermaid** → SVG — схемы потоков
- **Carbon.now.sh** — красивые скриншоты кода
