### Фаза A: Исследование (шаги 1–7)

1. **Plaud** — запись обсуждения идеи → автоматическая расшифровка и summary
2. **GPT Pro (Thinking)** — deep research: рынок, конкуренты, аудитория
3. **Opus** — составление GDD (модульная структура: Core, Arena, Combat, Economy, UI...). GDD разбивается на 5–8 частей — это экономит контекстное окно агентов и каждая часть позже становится основой отдельного модуля в архитектуре. Разбиение можно доверить Opus
4. **Кросс-ревью GDD** — GPT, Gemini, DeepSeek (2–4 итерации)
5. **Opus** — архитектурный документ на базе GDD
6. **Кросс-ревью архитектуры** — те же модели, до консенсуса

### Фаза B: Настройка рабочего места (шаги 8–9)

7. **GitHub** — fork/создание репо, branch protection, CODEOWNERS, CI/CD
8. **Настройка окружения ИИ-агентов** — подробно в Части 4

### Фаза C: Разработка (шаги 10–19)

9. **PM-Opus** планирует спринт → согласование с оператором
10. **Developer-субагенты** реализуют задачи
11. **Reviewer-субагенты** — ревью по 3 аспектам (архитектура, безопасность, качество)
12. **Внешние ревьюверы** — GPT-5.4, Codex, Copilot (ручной запуск)
13. **Автотесты** → **Ручное тестирование** → **Merge** (только оператор)
14. **Release** → **Deploy** (GitHub Actions + Docker). ИИ-агенты также участвуют в деплое: пишут ТЗ на инфраструктуру (watchdog, масштабирование), настраивают удалённые серверы через SSH, генерируют скрипты бэкапов. Но DevOps-задачи требуют повышенного контроля оператора — каскадные сбои (см. Часть 5)

### PR как средство коммуникации между агентами

> **Ключевой инсайт:** Pull Request — это не просто мерж-реквест, а **шина обмена информацией** между разными ИИ-агентами.

```
Developer (Opus) ──push──► PR #42
                              │
PM (Opus) ──────── gh pr comment ──► "Developer Report: ..."
                              │
Reviewer 1 (Opus) ─ gh pr comment ──► "Review: APPROVED"
Reviewer 2 (GPT)  ─ gh pr comment ──► "Review: CHANGES_REQUESTED"
Reviewer 3 (Copilot)─ gh pr comment ──► "Review: APPROVED"
                              │
PM (Opus) ──────── парсит комменты ──► консенсус 2/3 → делегирует фикс
                              │
Developer (Opus) ──push──► фикс
                              │
Reviewers ──────── ре-ревью ──► консенсус 3/3 ✅
                              │
Оператор (человек) ──────── merge
```

**Почему PR, а не чат:**

- Аудиторский след (кто, когда, какой вердикт)
- Разные модели (GPT, Gemini, Opus) пишут в одно место
- PM парсит JSON-метаданные из комментариев для автоматизации
- Оператор видит всю историю решений в одном месте

### 4.2 `settings.json` — два уровня защиты

```jsonc
{
  "permissions": {
    "allow": [
      "Bash(*)",        // Все bash-команды (защита через deny-list ниже)
      "Read", "Edit", "Write",  // Файловые операции
      "Glob", "Grep",   // Поиск файлов и текста
      "WebFetch", "WebSearch",  // Интернет (для research)
      "TodoWrite",       // Управление задачами в сессии
      "Task",            // Запуск субагентов
      "NotebookEdit"     // Jupyter-ноутбуки
    ],
    "deny": [
      // 🔒 Защита секретов
      "Read(.env*)",              // .env файлы с API-ключами
      "Read(**/credentials*)",    // Файлы с учётными данными
      "Read(**/secrets*)",        // Файлы с секретами

      // 🔒 Защита от удаления (Linux + Windows)
      "Bash(rm -rf:*)",           // Рекурсивное удаление
      "Bash(rm *)",               // Удаление файлов
      "Bash(del *)",              // Windows: удаление файлов
      "Bash(rmdir *)",            // Windows: удаление директорий

      // 🔒 Защита git (КРИТИЧНО)
      "Bash(git push --force *)", // Force push
      "Bash(git push -f *)",      // То же, короткая форма
      "Bash(git push origin main)", // Push в main

      // 🔒 Защита GitHub (только человек мержит)
      "Bash(gh pr merge *)",      // Автоматический merge PR
      "Bash(gh repo delete *)",   // Удаление репозитория
      "Bash(gh api -X DELETE *)"  // DELETE-запросы к GitHub API
    ],
    "defaultMode": "acceptEdits"  // Авто-принятие правок файлов
  },
  "language": "russian",               // Русский язык ответов
  "alwaysThinkingEnabled": true        // Extended thinking (глубокий анализ)
}
```

**Зачем deny-list:**

- Агент физически не сможет выполнить `git push origin main` — даже если в промпте ошибка
- Это **второй уровень защиты** после правил в `AGENT_ROLES.md`
- Правила можно обойти (агент "забудет"), а deny-list — нельзя

### 4.3 Три столпа пайплайна

Весь процесс держится на трёх столпах. Каждый из них настолько силён, что способен значительно усилить даже вайб-кодинг в одиночку. Но вместе они превращают его в агентно-ориентированную разработку.

| Столп | Что это | Почему критичен |
|-------|---------|-----------------|
| **0. Подробные ТЗ** | GDD, архитектурный документ, RFC — написанные совместно с ИИ | Без ТЗ агент не знает, **что** строить. Документация — контракт между человеком и агентами |
| **1. Memory Bank** | Внешняя память между сессиями (`.memory_bank/`) | Без памяти агент каждую сессию начинает с нуля — переоткрывает решения, не знает контекста |
| **2. Beads** | Задачи как код, CLI-first (`.beads/`) | Без задач агент не знает, **что делать дальше**. Beads даёт приоритеты, зависимости, историю. Плюс позволяет агенту удерживать фокус — выявленные проблемы сбрасываются в задачи (`bd create`), не отвлекаясь на их решение |

**Столп 0** — нулевой, потому что он предшествует коду. Прежде чем настраивать Memory Bank или Beads, нужен исчерпывающий документ: GDD, архитектура, ТЗ. Его тоже пишет ИИ (Opus + кросс-ревью GPT/Gemini/DeepSeek), но утверждает человек.

### 4.4 Memory Bank — внешняя память между сессиями

> Концепция на основе статьи [«Memory Bank: устойчивый контекст для ИИ-агентов»](https://habr.com/ru/articles/979624/) (Максим Ткачев, bquadro, декабрь 2025)

| Файл | Обновляется | Кем |
|------|-------------|-----|
| `projectbrief.md` | Редко | Оператор |
| `productContext.md` | Редко | Оператор |
| `techContext.md` | При смене стека | Developer |
| `systemPatterns.md` | При архитектурных решениях | Architect |
| **`activeContext.md`** | **Каждую сессию** | **PM / Developer** |
| **`progress.md`** | **Каждый спринт** | **PM** |

**Без Memory Bank:** агент каждую сессию начинает с нуля, переоткрывает те же решения, не знает контекста.
**С Memory Bank:** агент читает `activeContext.md` и сразу понимает, что было сделано, что в работе, какие проблемы.

### 4.5 Beads — задачи как код

```yaml
# .beads/config.yaml
sync-branch: "beads-sync"    # Ветка для синхронизации задач
```

Beads хранит задачи в `.beads/issues.jsonl` (JSONL) + SQLite. Агенты работают с задачами через CLI:

```bash
bd ready                          # Доступные задачи
bd update <id> --status=in_progress  # Взять в работу
bd close <id> --reason="PR #42"     # Закрыть с причиной
```

**Почему CLI-first, а не Jira/Linear?**

- Агент работает в терминале. `bd ready` → `bd update` → `bd close` — три команды, ноль переключений контекста
- Задачи хранятся в `.beads/` внутри репозитория — часть кода, а не внешний сервис
- Зависимости между задачами (`bd dep add`) — агент видит, что заблокировано

**Альтернативы:** GitHub Issues, Linear, Jira — но Beads оптимален для CLI-first агентов.

> Подробнее: [«Beads: система памяти для кодинг-агентов»](https://habr.com/ru/articles/983498/) (Хабр)

## Часть 5. Что не удалось победить — честный разбор (5 мин)

> Слайды 16–19

### 5.1 Обзор проблем

| Проблема | Статус | Workaround |
|----------|--------|------------|
| God Objects | ⚠️ | Рефакторинг каждые 2 недели |
| Цикл ревью обрывается | ⚠️ | Ручной запуск каждой итерации |
| Язык комментариев | ⚠️ | Отдельные PR на исправление |
| Безопасность | ⚠️ | Кросс-ревью разными моделями |
| Инфраструктура | ⚠️ | Повышенный контроль оператора |
| Gemini как ревьювер | ❌ | Отказ от роли ревьювера |

### 5.2 God Objects — правило-защитник стало причиной

ArenaRoom.ts — 3700+ строк, 126 методов. main.ts — 4000+ строк.

**Причина:** агенты следуют принципу "минимальное изменение" из CLAUDE-core.md и добавляют код в существующий файл, а не создают новый модуль.

**Решение: регулярный рефакторинг.** На всех трёх проектах рефакторинг проводился успешно — ИИ-агенты хорошо справляются с декомпозицией, когда задача поставлена явно. Рецепт: ревизия каждые 2 недели, выделение модулей до того, как файл станет неуправляемым. God Objects — не приговор, а сигнал к плановому рефакторингу.

### 5.3 Агенты не следуют инструкциям

**Итерационный цикл ревью обрывается.** PM запускает цикл код → ревью → фикс, но после первого исправления цикл останавливается. Реально нужно 3–7 итераций. PR #5 в Bonk Race: GPT нашёл coin farm, Developer «исправил», на третьей итерации — тот же баг. ~30% циклов завершаются полностью.

**Язык комментариев.** Правило "комментарии только на русском" прописано в CLAUDE.md, AGENT_ROLES.md, copilot-instructions.md — работает ~70% случаев. PR #21 — отдельный PR только на исправление языка. Причины: модели обучены на англоязычном коде, при сжатии контекста правило выпадает первым.

**Порочный круг потери контекста.** Субагент запускается в чистом контексте, не видит историю. После compaction инструкции об обновлении Memory Bank выпадают. Агент не обновляет Memory Bank → следующий агент не видит контекста → повторяет ошибки. Решение: не стесняйтесь переспрашивать и напоминать.

### 5.4 Слабые места

**Безопасность:** Coin farm (P0), отсутствие идемпотентности (P1), сломанный guest auth (P1). Всё нашёл GPT при ревью, Developer-Opus не исправил за 3 итерации. Вывод: кросс-ревью разными моделями критично именно для безопасности. GPT — лучший внешний ревьювер для Claude-разработчика.

**Инфраструктура:** Три withdrawn-версии Docker. Redis — 22 часа даунтайма. За несколько итераций деплой настроили, но для коммерческих продуктов доверять DevOps агентам пока рано.

### 6.2 Эмоциональная кривая ИИ-разработки

> По мотивам статьи [«Цветы для Элджернона и Claude Code»](https://vc.ru/ai/2800102) (Nolan & Claude, перевод Сергей Дургалян)

Рядом с технической шкалой есть эмоциональная — и о ней никто не предупреждает.

| Фаза | Период | Проект | Что чувствуешь |
|------|--------|--------|----------------|
| 1. Эйфория | ноябрь 2025 | U2 | «За часы — то, на что раньше ушло бы месяцы». Камень в животе, огонь в голове. Одновременно |
| 2. Затухание | декабрь–январь | Slime Arena | «Вау» требует всё больших запусков. Остальная жизнь ощущается как пауза между сессиями |
| 3. Плато | март | Bonk Race | Ты не уверен: принял ситуацию или просто перестал чувствовать |

**Почему это важно для инженерного доклада:**

- Эйфория Фазы 1 приводит к переоценке возможностей и God Objects
- Затухание Фазы 2 — когда процесс становится рутиной, нужна **инфраструктура** (Memory Bank, Beads, роли), а не энтузиазм
- Плато Фазы 3 — устойчивая продуктивность возможна, но требует осознанного управления своим вниманием

**Вывод:** Agentic Engineering — это не только настройка файлов. Это управление собственным вниманием и энергией при работе с инструментом, оптимизированным для удержания.
