## [1:30–4:00] Часть 1. Agentic Engineering — что это и зачем (слайды 2–3)

### Слайд 2: Vibe Coding vs Agentic Engineering

Vibe coding — когда сидишь в чате и пишешь: «сделай кнопку», «добавь авторизацию», «почему не работает?». Для прототипов годится, для серьёзных проектов — нет. Нет воспроизводимости, нет контроля качества, нет документации.

Agentic Engineering — другой подход. Один раз настраиваешь рабочее место для ИИ-агентов: роли, правила, файлы конфигурации, системы контроля. Дальше ИИ работает по этим правилам. Он знает все языки, фреймворки, паттерны — но не знает контекст вашего проекта. Ваша задача — дать ему этот контекст.

В vibe coding контроль — ваши глаза. В agentic engineering — тесты, ревью, вердикты.

### Слайд 3: Три проекта

За зиму три проекта. Первый — U2 в декабре — эксперимент, можно ли вообще так работать. Второй — Slime Arena в январе — 83 тысячи строк TypeScript за 31 день, готово к Soft Launch. Третий — Bonk Race, начало марта, всего 7 дней — форк Slime Arena, довёл пайплайн до текущего состояния.

На каждом проекте улучшал сам процесс. То, что покажу сегодня — результат трёх итераций.

## [4:00–6:00] Часть 2. Стек нейросетей (слайды 4–5)

### Слайд 4: Кто за что отвечает

Важный принцип: разные модели для разных задач.

**Claude Opus 4.6** — основной инструмент. PM, архитектор, разработчик, ревьювер. Лучше всех следует сложным инструкциям. 30-страничный документ с правилами — прочитает и будет следовать. Другие модели теряют правила на половине.

**GPT-5.4 и GPT-5.3-Codex** — ревьюверы. Следуют роли: сказал «только ревью, не правь код» — не правит. Находит реальные баги, не придуманные.

**GPT Pro (Thinking)** — глубокий анализ. Рынок, конкуренты, аудитория. Запускаешь, уходишь пить кофе, через полчаса получаешь отчёт.

**Gemini** — пробовал как ревьювера, не вышло. Пишешь «НЕ ПРАВЬ КОД» — правит. Выдаёт ложные APPROVED, пропуская критические баги. Отказался от этой роли. Зато хорош в составлении промптов для MidJourney — сокращает число итераций генерации раза в три.

**Copilot** — код вручную не пишу, автодополнение не нужно. Использую как ревьювер PR.

**DeepSeek** — бесплатный, контекстное окно короткое. Для ревью кода не подходит, но для ревью документов и ТЗ полезен.

**MidJourney** — концепт-арт и ассеты. В пайплайн разработки не интегрируется — отдельный процесс.

**Plaud** — hardware для записи встреч. Записывает, расшифровывает, делает summary. Начало любого проекта — записанная встреча.

### Слайд 5: Принцип выбора

Дорогие модели — для архитектуры и планирования. Быстрые и дешёвые — для рутины. Несколько моделей параллельно для ревью — одна модель пропустит баг, три — вряд ли.

## [6:00–9:00] Часть 3. Процесс: от идеи до деплоя (слайды 6–10)

### Слайд 6: Обзор процесса

Три фазы: исследование, настройка рабочего места, разработка. Сейчас кратко пройдусь по каждой.

### Слайд 7: Фаза A — Исследование

Начинается с живой встречи. Plaud записывает, через час — транскрипт и summary. Это бриф.

GPT Pro в режиме Deep Research — рынок, конкуренты, аудитория. Opus пишет GDD — модульную структуру: Core, Arena, Combat, Economy, UI. Разбиение на 5–8 частей — не прихоть. Это экономия контекстного окна: будущие агенты будут работать с отдельными частями, а не грузить весь документ. И каждая часть GDD потом становится основой для отдельного модуля в архитектуре. Разбиение можно доверить ИИ — Opus хорошо с этим справляется.

Кросс-ревью: GDD отдаю трём моделям — GPT, Gemini, DeepSeek. 2–4 итерации до консенсуса. Тот же цикл для архитектуры.

### Слайд 8: PR как шина коммуникации

Pull Request — не просто способ замержить код. Это шина обмена информацией между разными ИИ-агентами.

Developer пушит код. PM публикует отчёт через `gh pr comment`. Три ревьювера (разные модели) пишут вердикты в комментарии к тому же PR. PM парсит комментарии, считает консенсус. Нужны исправления — создаёт задачу, Developer пушит фикс, ревьюверы перепроверяют.

Разные модели, разные инструменты — одна точка сбора. Оператор открывает PR и видит всю историю решений.

### Слайд 9: PR — поток работы

Developer-Opus пушит код в ветку. PM публикует Developer Report. Запускаются ревьюверы: внутреннее ревью — Opus, внешнее — GPT, Copilot. Собираем вердикты. Нужен консенсус. Нет — фикс и ещё итерация. Да — merge. Merge — только я.

### Слайд 10: Почему PR, а не чат

Аудиторский след — кто, когда, какой вердикт. Мультимодельность — GPT, Gemini, Opus пишут в одно место. Автоматизация — PM парсит метаданные для следующей итерации. Оператор видит всё в одном месте.

## [9:00–13:00] Часть 4. Конфигурация и три столпа (слайды 11–15)

### Слайд 11: Какая модель читает какие файлы

Несколько ИИ-инструментов, каждый читает свои файлы.

Claude Code читает `CLAUDE.md` при запуске. Оттуда по ссылкам подгружает остальные. Плюс `.claude/settings.json` — разрешения и запреты.

Copilot читает `.github/copilot-instructions.md`. `CLAUDE.md` не видит. Отдельный файл с подмножеством правил.

Cursor — `.cursorignore` для индексации, можно добавить `CLAUDE.md` как project rule.

GPT и Gemini — ничего не читают автоматически. Контекст вставляете в промпт вручную.

Точка конвергенции — `.agents/AGENT_ROLES.md`. Его читают все.

### Слайд 12: settings.json — два уровня защиты

Allow-list — что агент может делать. Deny-list — что не может ни при каких обстоятельствах: читать `.env`, удалять файлы, `git push --force`, `git push origin main`, мержить PR, удалять репозиторий.

Зачем deny-list, если правила прописаны в AGENT_ROLES.md? Правила — первый уровень защиты. Агент может «забыть» правило. Deny-list — второй уровень. Хардкод на уровне инструмента. Не обойти.

### Слайд 13: Три столпа пайплайна

Весь мой процесс держится на трёх столпах. Каждый из них настолько силён, что способен значительно усилить даже вайб-кодинг в одиночку. Но вместе они превращают его в агентно-ориентированную разработку.

Столп ноль — подробные ТЗ. GDD, архитектурный документ, RFC. Их тоже пишет ИИ — Opus составляет, GPT и Gemini ревьюят, — но утверждает человек. Контракт между человеком и агентами.

Столп один — Memory Bank. Шесть Markdown-файлов. Без них агент каждую сессию начинает с нуля.

Столп два — Beads. Задачи как код. `bd ready`, `bd update`, `bd close`. Три команды, ноль переключений контекста. Задачи в репозитории — часть кода, а не внешний сервис. Плюс агент может сбросить найденную проблему в задачу и не отвлекаться — удерживает фокус.

Стартер-кит — настройки инструмента. Три столпа — процесс. Настройки без процесса бесполезны.

### Слайд 14: Memory Bank

Концепцию взял из статьи Максима Ткачева на Хабре — «Memory Bank: устойчивый контекст для ИИ-агентов». Это самая важная часть моего опыта.

Без Memory Bank каждая сессия Claude Code начинается с нуля. С ним — агент читает `activeContext.md` и сразу в курсе: версия, последний PR, проблемы, техдолг.

Шесть файлов:

- `projectbrief.md` — зачем проект (редко)
- `productContext.md` — продуктовый контекст (редко)
- `techContext.md` — стек и ограничения (при смене стека)
- `systemPatterns.md` — архитектурные паттерны (при арх. решениях)
- `activeContext.md` — что сейчас происходит (каждую сессию)
- `progress.md` — прогресс и статус (каждый спринт)

### Слайд 15: Beads

Задачи как код. CLI-first: `bd ready` — доступные задачи, `bd update` — взял в работу, `bd close` — закрыл.

Можно использовать GitHub Issues или Linear. Beads удобнее для агентов — CLI-first, агент не ходит в браузер.

## [13:00–18:00] Часть 5. Что не удалось победить (слайды 16–19)

### Слайд 16: Обзор проблем

Реальные проблемы, которые не решил до конца за три месяца.

God Objects. Цикл ревью обрывается. Язык комментариев. Безопасность. Инфраструктура. Gemini как ревьювер. Таблица с проблемами и workaround'ами на слайде.

### Слайд 17: God Objects — правило-защитник стало причиной

ArenaRoom.ts — 3700 строк, 126 методов. main.ts — 4000 строк. Правило «минимальное изменение» привело к тому, что агенты добавляют код в существующий файл вместо создания нового модуля.

Но это решаемо. На всех трёх проектах рефакторинг проходил успешно — агенты хорошо декомпозируют, когда задача поставлена явно. Рецепт: ревизия каждые 2 недели. God Objects — не приговор, а сигнал к плановому рефакторингу.

### Слайд 18: Агенты не следуют инструкциям

Цикл ревью обрывается. PM запускает цикл: код → ревью → фикс → ре-ревью. После первого исправления цикл останавливается. PR #5 в Bonk Race: GPT нашёл coin farm, Developer «исправил», на третьей итерации — тот же баг. Примерно 30% циклов завершаются полностью.

Язык комментариев. Правило в трёх файлах. Работает в 70% случаев. PR #21 — отдельный PR только на исправление языка. Модели обучены на английском коде, при сжатии контекста правило выпадает первым.

Порочный круг потери контекста. Субагент запускается в чистом контексте, не видит историю. Агент не обновляет Memory Bank → следующий агент не видит контекста → повторяет ошибки. Не стесняйтесь переспрашивать и напоминать.

### Слайд 19: Слабые места

Безопасность: Coin farm, отсутствие идемпотентности, сломанный guest auth. Всё нашёл GPT при ревью. Developer-Opus не исправил за 3 итерации. Кросс-ревью разными моделями — необходимость именно для безопасности. GPT — лучший внешний ревьювер для Claude-разработчика.

Инфраструктура: Три withdrawn-версии Docker. Redis — 22 часа даунтайма. За несколько итераций деплой настроили — агенты писали ТЗ, конфиги Docker, systemd-сервисы, скрипты бэкапов. Но для коммерческих продуктов доверять DevOps агентам пока рано.

## [18:00–25:00] Часть 6. Где мы на карте (слайды 20–21)

### Слайд 20: 8 уровней агентной инженерии

Есть статья на Хабре — «8 уровней агентной инженерии». Шкала от 1 (автодополнение) до 8 (автономные команды агентов).

Мы на четвёртом уровне — накопление опыта. Memory Bank фиксирует уроки, правила обновляются между сессиями. Частично пятый — MCP (Beads). Частично шестой — Zero Trust, мультивендорное ревью, CI.

Чего не хватает: цикл обратной связи не замкнут, человек всё ещё сливает PR вручную.

Три вопроса:

1. На каком уровне вы сейчас? Большинство — на втором-третьем.
2. Что мешает перейти на следующий?
3. Готовы инвестировать в инфраструктуру уровней 3–5, чтобы разблокировать 6–7?

### Слайд 21: Эмоциональная кривая

Есть статья — «Цветы для Элджернона и кривая Claude Code». Эмоциональный цикл работы с ИИ. Три фазы.

Фаза 1 — Эйфория. Ноябрь, U2. Собираешь за часы то, на что раньше ушло бы месяцы.

Фаза 2 — Затухание. Декабрь-январь, Slime Arena. «Вау» требует всё больших запусков. Остальная жизнь — пауза между сессиями.

Фаза 3 — Плато. Март, Bonk Race. Не уверен: принял или перестал чувствовать.

Почему это важно: эйфория — когда создаются God Objects. Затухание — когда нужна система, а не энтузиазм. Стартер-кит — страховка от того момента, когда эйфория закончится.

## [30:00+] Q&A — заготовленные ответы (слайды 26–27)

### «Сколько это стоит?»

Claude Opus — $100–200/мес на API. GPT для ревью — $20–40. Итого $120–240/мес.

### «А что с конфиденциальностью кода?»

Код идёт в API Anthropic/OpenAI. Если критично — self-hosted модели или проверьте compliance-политики. Для большинства проектов стандартные ToS достаточны.

### «Можно ли в команде?»

Да. CLAUDE.md и settings.json коммитятся в репо — одни правила для всех. Memory Bank общий. Мультиагентные сессии пока однопользовательские.

### «Когда НЕ подходит?»

- Banking, medical — нужен human review
- DevOps — агенты плохо справляются
- Легаси без тестов — нечем проверить
- 100% in-house code (compliance)
